# Архитектура и инженерные решения

Каждый проект имеет собственные сущности, DbContext, миграции, контейнеры и тесты. Общего runtime-кода между приложениями нет: их можно развивать независимо. Solution объединяет проекты для удобства сборки.

```text
Api ────────────────> Application ────────> Domain
 │                         ↑
 └──> Infrastructure ──────┘
```

`Domain` хранит сущности с закрытыми setters и проверками инвариантов. `Application` содержит сценарии, DTO и узкий порт `IStore`. `Infrastructure` реализует этот порт через EF Core и Npgsql. `Api` связывает зависимости, сопоставляет HTTP-маршруты со сценариями и переводит ошибки в ProblemDetails.

## SOLID в коде

- **SRP:** Routes отвечает за HTTP, AppService — за сценарии, сущности — за корректность состояния, EfStore — за запросы и транзакции.
- **OCP:** инфраструктуру можно заменить реализацией `IStore`; новые приоритеты и сроки SLA добавляются данными без изменения C#-ветвлений. Новые бизнес-возможности могут требовать изменения интерфейсов — проект не обещает расширение без правок любого кода.
- **LSP:** реализация `IStore` обязана соблюдать контракт. Например, `Reserve` атомарно списывает остаток и сохраняет заказ либо не сохраняет ни одно изменение.
- **ISP:** порт принадлежит конкретному приложению; нет универсального `IRepository<T>` с неиспользуемыми методами.
- **DIP:** AppService принимает `IStore`, не знает о DbContext и PostgreSQL. Регистрация зависимостей находится в composition root API.

Дополнительный Unit of Work поверх DbContext не введён. CQRS-фреймворк, брокер сообщений и микросервисные вызовы не нужны для этих небольших сценариев.

## StockFlow: целостность остатков

Создание заказа использует условный SQL UPDATE: остаток уменьшается только при `Stock >= Quantity`. Число изменённых строк определяет успех. Списание и INSERT заказа находятся в одной транзакции. Два параллельных запроса на последнюю единицу не могут оба создать заказ.

Отмена сначала атомарно меняет `Confirmed` на `Cancelled`, затем возвращает остаток в той же транзакции. Повторная отмена отвечает 409. Цена фиксируется в сумме заказа в момент создания. Ограничения CHECK и внешний ключ дополняют доменную валидацию.

Граница модели: один товар в заказе, без оплаты, пополнения склада и повторной отправки заказа по idempotency key. Защита от overselling не делает POST идемпотентным: повторный успешный POST создаст второй заказ.

## ExpenseLens: аналитика из данных

Категория определяет ежемесячный бюджет. Отчёт возвращает все категории, включая категории без расходов. Расходы фильтруются полуоткрытым интервалом `[начало месяца, начало следующего месяца)`, сумма считается SQL-агрегацией. Индекс `(CategoryId, Date)` соответствует фильтру. Отрицательные суммы, нулевые суммы и дробные копейки отклоняются.

Деньги: `decimal` в C#, `numeric(18,2)` в PostgreSQL. Даты расходов — `DateOnly`, чтобы часовые пояса не переносили расход в другой месяц. Нет конвертации валют или исторических версий бюджета.

## SupportDesk: Data-driven SLA

Приоритеты не зашиты в enum или switch: таблица `Policies` определяет название приоритета и время решения. При создании обращения приложение находит правило и фиксирует DueAt. Политика влияет на новый тикет через данные; существующий срок уже является снимком правила.

Переходы: `Open → InProgress → Resolved`. Клиент передаёт Version из последнего GET. Домен отклоняет устаревшую версию, а EF concurrency token защищает от изменения между чтением и записью в двух разных запросах. `TimeProvider` передаётся через DI; даты хранятся в UTC. Список просроченных обращений ограничен 100 строками и сортируется по DueAt.

## HTTP, эксплуатация и проверка

Создание товара, заказа, категории, расхода и обращения возвращает 201 и рабочий Location. Создание SLA-правила возвращает 200 с правилом. Ошибки валидации — 400, отсутствующие ресурсы — 404, конфликт состояния/конкуренции/уникальности PostgreSQL — 409. Неожиданные ошибки журналируются, клиент получает 500 без внутреннего stack trace. Синтаксические ошибки JSON и привязки параметров обрабатывает ASP.NET Core.

`/health/live` проверяет процесс, `/health/ready` — доступность БД. Docker запускает API от пользователя `app`; миграции выполняются отдельным одноразовым SDK-контейнером перед API. В production следует вынести выполнение миграций в контролируемый этап deployment, добавить auth, TLS, rate limits и управление секретами.

Быстрые тесты проверяют бизнес-сценарии с SQLite. Тестовый адаптер типов не проверяет Npgsql translation. Для этого предусмотрен отдельный CI job с PostgreSQL и настоящими миграциями; Docker smoke test дополнительно проверяет полный запуск контейнерного стека.
